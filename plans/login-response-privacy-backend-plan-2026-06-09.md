# Login Response Privacy Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Change `POST /api/user/login` so it returns only the minimum authentication and routing fields needed by the frontend, and stops returning personal privacy fields such as address, birthdate, phone number, and email.

**Architecture:** Keep the existing login route, username-or-email request behavior, Spring Security authentication flow, and JWT generation. Replace login's response mapping from the broad `UserDTO` to the existing dedicated `LoginResponseDTO`, populated only with a flat minimal response contract for current frontend compatibility. Do not add a profile endpoint in this issue, because the current backend README notes that JWT is generated but not enforced by a request filter; an unauthenticated profile endpoint would move the privacy leak instead of fixing it.

**Tech Stack:** Java 17, Spring Boot 3.2.3, Maven, Spring Web, Spring Security, JJWT, Lombok, Jackson, JUnit 5.

## Required API Contract

Keep request unchanged:

```json
{
  "username": "employee_username_or_email@example.com",
  "password": "raw-password"
}
```

Return a flat minimal response to reduce frontend blast radius:

```json
{
  "username": "employee1",
  "name": "Employee One",
  "roles": "tester|Manager",
  "groupName": "surrey",
  "jsessionID": "03BF94E92873D84D44D2B1FBA27F3B0A",
  "token": "eyJhbGciOiJIUzI1NiJ9.example.signature"
}
```

Field rules:

- Keep `username`: canonical persisted username. Required.
- Keep `name`: display name used by the current UI. Required when available.
- Keep `roles`: current persisted role string. Required because frontend route and permission checks parse it.
- Keep `groupName`: low-sensitivity routing/scope context used by current frontend flows. Nullable.
- Keep `jsessionID`: temporary compatibility field because current frontend code reads `localStorage.user.jsessionID` for some shift requests. Prefer `jsessionID` on the wire; if Jackson currently emits `JSessionID`, either explicitly annotate the DTO property or make the frontend migration accept both names during rollout.
- Keep `token`: JWT generated by `JwtUtil.generateToken(user)`. Required.
- Remove `email`, `phoneNumber`, `address`, `birthdate`, `legalname`, `sinno`, `password`, `personalDocumentsPath`, `personalDocuments`, `active`, and `bigDay` from login response.

No database change is required:

- No new table.
- No new column.
- No constraint change.
- No data migration.
- No SQL for user execution.

## Backend Acceptance Criteria

- `POST /api/user/login` still accepts username or email in `LoginDTO.username`.
- Authentication behavior and JWT subject remain unchanged.
- Login response includes `username`, `name`, `roles`, `groupName`, `jsessionID`, and `token`.
- Login response does not include `email`, `phoneNumber`, `address`, `birthdate`, `legalname`, `sinno`, `password`, `personalDocumentsPath`, `personalDocuments`, `active`, or `bigDay`.
- `UserDTO` may remain broad for existing profile modification and query flows, but it is no longer used as the login response DTO.
- No database table, field, constraint, or migration is required.

## Cross-Stack Handoff To Frontend

Frontend must update `UserRequest.login(...)` and `UserService.login(...)` to use the same flat minimal response shape:

```ts
export interface LoginResponse {
  username: string;
  name: string;
  roles: string;
  groupName?: string | null;
  jsessionID?: string | null;
  token: string;
}
```

Frontend should store only this minimal response in `localStorage.user`. Components that currently read profile/privacy fields from `localStorage.user` must stop doing so.
